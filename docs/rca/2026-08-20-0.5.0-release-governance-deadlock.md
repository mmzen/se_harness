# RCA: 0.5.0 release governance deadlock

| Field | Value |
| --- | --- |
| Status | Closed |
| Incident date | 2026-08-19 to 2026-08-20 |
| Scope | `se_harness` governance and release process |
| User impact | No runtime outage; the 0.5.0 release was blocked and release controls required emergency recovery |
| Final outcome | `0.5.0a1` bootstrap release, standard-root conversion, then final `0.5.0` release |

## Executive summary

The 0.5.0 release became blocked because the `se_harness` repository was still treated as a special self-hosting repository. The same developing product was therefore involved both as the repository being governed and as the tool governing that repository.

During the attempted upgrade, candidate `se_harness` code was used to create or manage lifecycle artifacts. Although those artifacts could match the candidate's newer format, they did not obtain authority from the independently released evaluator governing the repository. Changing only the configured governor version could not repair this: the governing runtime, its immutable distribution, the installed root, and the formal approval chain also had to agree.

This produced a circular dependency: changing the governor required authorization from the existing governor, while the intended change removed the special lifecycle through which that authorization was expected to occur.

Recovery used a one-time bootstrap. An immutable `0.5.0a1` was published without relying on the blocked harness controls. That public release was installed in an isolated environment and used as the independent evaluator to convert the repository to the normal standard-repository lifecycle. The final 0.5.0 candidate was then validated separately, published, publicly verified, and the normal publisher was restored.

This was a process and architecture failure, not an individual failure.

## Authority boundary

This RCA is supporting retrospective documentation. It does not approve work, verify a candidate, release software, authorize the emergency publications retroactively, or promote the abandoned local draft artifacts. The recommendations are tracked in [GitHub issue #81](https://github.com/mmzen/se_harness/issues/81), and each implementation requires its own governing chain and accountable approval.

## Impact

- The planned 0.5.0 release and CI harness upgrade could not proceed through the existing governance path.
- Draft work-order and release artifacts were not safely promotable because their evaluator provenance and governing chain were inconsistent.
- Time was spent extending approval chains that could not resolve the underlying circular dependency.
- A temporary emergency publishing workflow had to replace normal release controls, increasing operational and supply-chain risk for a bounded period.
- No consumer runtime outage or compromised publication was observed.
- The inconsistent formal artifacts remained drafts and were not silently promoted or used to authorize the final release.

## Detection

The harness controls eventually failed closed: the artifacts did not pass the governing checks even though they had been produced with newer `se_harness` code. The decisive diagnosis was that candidate product code and the released governing evaluator had been mixed.

The detection was correct but late. The system rejected the resulting authority mismatch only after substantial drafting and sequencing work; it did not prevent candidate code from being used for root lifecycle operations at the start.

## Root cause

The root cause was the special self-hosting lifecycle maintained by the `se_harness` repository. It blurred a boundary that must remain strict:

- Candidate source and candidate packages are the product under development and may produce only candidate evidence.
- A repository governor must be an already released, immutable evaluator installed independently from the checkout.

Because the repository carried separate self-hosting metadata and workflow behavior, upgrading the product and upgrading its governor became one coupled operation. That coupling created an authority cycle and made it possible to treat candidate code as a de facto governor.

### Five whys

1. **Why could 0.5.0 not proceed normally?** The governing controls rejected the lifecycle artifacts needed to authorize and release it.
2. **Why were the artifacts rejected?** They were created or managed with candidate tooling rather than through the independently released evaluator and its valid governing chain.
3. **Why was candidate tooling used for governance?** The repository's special self-hosting model combined product development and governor lifecycle operations.
4. **Why did changing the configured version not fix it?** A version string does not establish authority; runtime origin, immutable distribution identity, installed state, and approvals must also be valid.
5. **Why was there no normal migration path out?** Removing the special lifecycle required authorization through that same lifecycle, and there was no previously defined pre-1.0 bootstrap procedure for breaking the cycle.

## Contributing factors

- The product release, CI evaluator upgrade, governor migration, and removal of self-hosting behavior were initially treated as parts of one release effort.
- The terms *developed harness*, *governor*, *self-hosted governor*, and *installed harness* did not make the trust boundary sufficiently obvious.
- Newer tooling could create syntactically valid artifacts before their authority provenance was resolved.
- Draft artifacts from multiple attempted governing chains accumulated and made the current authoritative path harder to see.
- The normal publisher assumed a valid formal release chain and had no documented, narrowly scoped bootstrap path for recovery from a governance deadlock.
- The repository-specific lifecycle made `se_harness` behave differently from the standard repositories it governs, so its own lifecycle was less representative and less exercised.

## Why the recovery was safe enough

The emergency path deliberately bypassed lifecycle authorization, but it retained independent technical controls:

- Both releases used immutable tags and exact commit checks.
- Publication used GitHub OIDC Trusted Publishing rather than a long-lived PyPI token.
- The built wheel and source distribution were published with SHA-256 checksums and PyPI attestations.
- The public packages were installed from PyPI in fresh environments rather than reused from the checkout.
- Runtime identity proved that the evaluator's modules, templates, Python executable, and entry point were outside the candidate checkout.
- The final candidate and the restored `main` branch passed hosted Engineering Harness and Candidate Evidence workflows.
- The temporary publisher was reverted immediately after publication.

These controls reduced the emergency risk; they do not retroactively turn the bypass into a normally governed release.

## What worked well

- Existing controls refused to accept invalid authority merely because the files matched a newer schema.
- The team stopped trying to repair the circular chain once the product/governor conflation was identified.
- The alpha bootstrap established a real, immutable external evaluator before root conversion.
- Root conversion and final version preparation were separate commits with narrow scopes.
- Obsolete draft artifacts were preserved for audit but excluded from release authority.
- The normal publisher and post-release CI were restored and verified before closing the incident.

## Preventive actions recommended

These recommendations are tracked in [issue #81](https://github.com/mmzen/se_harness/issues/81). The RCA and issue grant no implementation authority.

| Priority | Action | Intended result |
| --- | --- | --- |
| P0 | Make root lifecycle commands prove that their runtime matches the root's locked, released evaluator identity; candidate roles must fail before artifact or lifecycle mutation. | Detect the product/governor mix at the first command rather than during later validation. |
| P0 | Add an automated invariant that `se_harness` root governance contains no special self-hosting profile, descriptor, workflow, packaged template, or promotion command. | Prevent reintroduction of the architectural cause. |
| P0 | Require release readiness to report the released-evaluator version, distribution digest, module origin, template origin, executable origin, and checkout boundary in one retained record. | Make the active authority unambiguous and auditable. |
| P1 | Document a maintainer-only bootstrap recovery runbook with explicit emergency approval, immutable source selection, isolated build, Trusted Publishing, public-install proof, and mandatory restoration steps. | Make a future deadlock recoverable without improvising controls. |
| P1 | Keep governor upgrades separate from product release work orders unless the dependency and sequencing are explicitly modeled. | Avoid recreating a circular release transaction. |
| P1 | Add a release-readiness check that identifies obsolete or conflicting draft governing chains without treating them as authority. | Reduce ambiguity while preserving audit history. |
| P2 | Use *released evaluator* consistently for the governing runtime and reserve *candidate* for source or packages under test. | Reduce terminology-driven boundary mistakes. |
| P2 | Exercise standard-root upgrades and the emergency runbook periodically in disposable repositories. | Detect lifecycle and recovery regressions before a real release. |

## Lessons

1. Being generated by a newer harness does not make an artifact authorized.
2. Changing a governor version string is not equivalent to changing the governing runtime and authority chain.
3. The software under development must never govern its own root lifecycle.
4. `se_harness` should follow the same standard-repository lifecycle as its consumers.
5. Emergency bypasses need a predefined, auditable path and an immediate return to normal controls.
