# Release contract: se-harness 0.14.0

## Lifecycle and authority

This contract is a definition. Its approval by the release owner authorizes
`WO-RLS-020` to be approved and started as separate acts; it authorizes no
candidate, build, verification record, release record, tag, publication or
deployment by itself. Every later step is the decision of the role that owns
it, recorded on the artifact it changes. The aggregate verification record
is `VREC-SEH-023`; the release record is `RLS-SEH-023`.

## Release unit

One `se-harness` 0.14.0 release derived from one clean candidate commit cut
from `main`: a recipe-bound reproducible wheel, a normalized source
distribution, a checksum manifest, a schema-2 bound distribution table, an
immutable `v0.14.0` tag, GitHub Release assets, publication of the same
qualified files to PyPI, the canonical `release/0.14` maintenance line

### What this release is for

The packaged surface changes by nothing but the version markers since
`v0.13.0`: `pyproject.toml`, `se_harness/__init__.py` and the README
install line. No template, evaluator module, contract JSON, hash-bound
class, lock schema, workflow template or skill changes; a consumer that
upgrades from 0.13.0 to 0.14.0 regenerates no managed file beyond the
version identity the lock records.

The release exists for its integration commit. The public Explorer
demonstration is release-bound (`SPEC-DPG-001` rules 5 to 7): it is
generated by the root generator at the release integration commit of the
released record. For `RLS-SEH-022` that commit is `09aa69f`, whose root was
0.12.0, so the demonstration still shows the previous page although 0.13.0
ships the designed self-contained Explorer. `WO-HUP-014` moved this
repository's root to 0.13.0 on `main` at `d005b98`; this release's
integration commit therefore carries the designed generator, and its Pages
job publishes the designed page. The release owner decided this route on
2026-09-02 over waiting for a content-bearing 0.14.0 and over amending the
release-bound publication contract.

## Compatibility and migration

0.14.0 changes no evaluator behaviour and no managed template. `upgrade`
from 0.13.0 rewrites the lock's evaluator identity and the version
substitutions in the managed files that carry it; nothing else moves. A
0.13.0 root reads a 0.14.0-written lock without change. Consumers on
0.13.0 gain nothing functional by upgrading; consumers on 0.12.0 or older
gain the designed Explorer exactly as 0.13.0 delivers it.

## Security and provenance

The build of record is recipe-bound and digest-pinned
(`release/build-recipe.json`, `release/build-toolchain.lock`, both
unchanged since `v0.12.0`); the release record binds the wheel and sdist
digests through a schema-2 distribution table; the publication workflow
moves only verified inert bytes into privileged jobs and the `pypi`
environment remains a separate human decision. Identity by version,
installed-payload digest and archive pair is unchanged.

## Rollback criteria and procedure

A defect found after publication is repaired forward by a successor
release; a published 0.14.0 is never withdrawn from PyPI. A consumer stays
on 0.13.0 by not upgrading.

Stop condition: the candidate commit is not an ancestor of the ref being
released, or `harnessctl release-unit --contract REL-SEH-025` reports an
`E-CIP-001` finding beyond the two predicted by construction above. The
remedy is a new contract naming a new candidate, never an in-place edit of
`gates`.
