# Specification: Rejected-version succession and predecessor-view preparation contract

## Scope

This specification defines active release-version cardinality and a repository-owned, contract-bound adapter for running predecessor `prepare-release` against one exact compatibility view. It preserves the released-0.5 trust direction, complete rejected-bootstrap history, and immutable candidate/VREC identities.

## Actors and external systems

- Candidate validation proves the complete graph and lifecycle semantics.
- Git supplies the exact governance commit, blob identities, and isolated sparse worktree.
- External released evaluator 0.5.0 alone generates predecessor-format RLS bytes.
- The repository adapter proves and imports those bytes.
- The existing bootstrap binder proves the installed evaluator and public wheel and attaches canonical evidence.
- Accountable owners separately approve work, verify a VREC, decide an RLS, and authorize external actions.

## Inputs

- One clean governance commit containing the verified aggregate and approved successor contract.
- Exact rejected predecessor-bootstrap RLS/contract paths and bytes selected from declared metadata, never an allowlist.
- Successor RLS ID, release contract, verified VREC, work-order set, version, owner, and optional tag.
- Exact external evaluator interpreter, entry point, wheel, old lock, and contract tuple.

Every path, Git object, sparse rule, artifact, relation, JSON value, digest, process output, environment value, and runtime origin is untrusted until checked.

## Outputs

- One predecessor-generated ready RLS imported at its canonical destination.
- Canonical compact UTF-8/LF evidence using schema `se-harness-predecessor-preparation-view-v1`.
- Record fields `preparation_view_evidence_path` and `preparation_view_evidence_sha256` bound atomically with the view evidence.
- Existing `se-harness-predecessor-bootstrap-v1` evaluator binding and sidecar, applied only after view preparation succeeds.
- Structured plan/apply output that identifies source commit, candidate, omitted history, record, evidence, digests, and whether any write occurred.

## State model

```text
complete clean graph
  -> validate candidate semantics
  -> derive exact closed rejected pair
  -> create exact-commit sparse worktree
  -> run isolated 0.5.0 prepare-release
  -> verify and import RLS + view evidence atomically
  -> bind canonical evaluator evidence atomically
  -> validate complete graph and byte preservation
  -> ready proposal for human release review
```

Any failure before the final state leaves the source repository unchanged or rolls back only the newly created RLS/view-evidence pair.

## Behavioral rules

1. **Active version claim.** Only `ready` and `released` release records claim a version; cardinality is at most one. Valid `rejected` records remain visible history but do not claim it.
2. **Released finality.** Once a released record exists, no ready successor for that version is permitted. External tag/publication immutability remains an independent mandatory check.
3. **Closed history selection.** The view omits exactly one rejected predecessor-bootstrap RLS and its one exact rejected declaring contract. Selection is derived from validated relations and tuple equality.
4. **Exact source.** The sparse worktree is detached at the selected full governance commit. Sparse configuration is local to that worktree, generated by the adapter, and compared with canonical expected bytes before execution.
5. **Bounded omission.** Git tree enumeration must prove that exactly the two selected paths are absent from the worktree and every other tracked file expected by the adapter is materialized. The source tree, index, and historical blobs remain unchanged.
6. **Canonical view evidence.** Evidence records schema, source commit/object format/tree, candidate commit/object format, successor IDs/version/work set, evaluator tuple, exact normalized command arguments, sparse-spec digest, and for each omitted artifact its path, ID, type, status, Git blob ID, byte length, and raw SHA-256.
7. **Isolation.** The adapter removes `PYTHONPATH`, disables user-site imports, uses the exact external interpreter with `-I`, verifies runtime identity, and supplies no credentials or network-dependent input.
8. **Predecessor-owned output.** The adapter may not synthesize RLS core metadata or body. It accepts the newly created file only when its ID, status, version, commit, object format, owner, contract, VREC, work set, tag, and canonical destination exactly match requested inputs.
9. **Atomic import.** The RLS and preparation-view evidence are exclusive-created together or neither remains. Existing or partial destinations fail without overwrite or repair.
10. **Full-graph replay.** After import and after bootstrap binding, candidate validation runs against the complete repository. Omitted history must resolve from the source commit and match every recorded identity and raw byte.
11. **Binder separation.** The preparation adapter cannot create evaluator-bootstrap evidence. The existing binder remains a separate plan/apply action and continues accepting only the single approved contract.
12. **Ordinary behavior.** Candidate `prepare-release` and validation apply active version cardinality consistently in schema-3 repositories; no predecessor view is available unless the exact schema-2 bootstrap preconditions hold.
13. **No authority.** Planning, preparing, importing, binding, and validating create technical proposals/evidence only.

## Error and recovery behavior

All malformed, ambiguous, dirty, linked, escaped, missing, changed, duplicated, contaminated, nondeterministic, or partially written states fail closed. Apply rechecks the complete plan immediately before each write. If a post-import check fails, only the exclusive new RLS and view evidence are removed after confirming their digests; historical and pre-existing files are never rolled back or overwritten.

## Data and interface contracts

The adapter is a repository-owned script with explicit `--repository`, `--release-record`, `--release-contract`, repeatable `--verification-record` and `--work-order`, `--version`, `--authorized-by`, optional `--tag`, external evaluator paths, and plan/apply modes. JSON output is canonical and contains no secrets or host-specific user path beyond normalized diagnostic placeholders.

The preparation-view evidence schema is closed: unknown or missing fields, duplicate JSON keys, noncanonical encoding, non-LF termination, unsafe paths, uppercase or malformed digests, unordered sets, and unsupported object formats fail.

## Security and privacy properties

- No arbitrary sparse pattern or omitted path is accepted from a user.
- Symlinks, junction escapes, alternate object databases, replacement Git executables, environment import contamination, and time-of-check/time-of-use changes are rejected or bounded by exact rechecks.
- Evidence contains normalized origins and bounded identities, not usernames, tokens, environment dumps, or credentials.

## Performance and capacity

The adapter performs bounded Git enumeration, two complete candidate validations, one predecessor preparation, and existing bootstrap binding. It uses existing repository/evidence size ceilings and process timeouts.

## Observability

Plan/apply results identify every validated phase, exact hashes, mutation count, rollback outcome, and failing invariant. Retained `WO-REB-006` evidence distinguishes full-graph candidate validation from compatibility-view predecessor preparation.

## Compatibility and migration

- Operational root configuration, schema-2 lock, released evaluator, historical RLS/REL/VREC files, and version remain unchanged.
- `REL-SEH-009`, `VREC-SEH-010`, and candidate C3 remain true historical governance/assurance facts but cannot promote after a C4 implementation change.
- A successor contract uses new identities; no prior candidate, VREC, RLS, or contract is repointed.

## Examples and counterexamples

- **Conforming:** rejected C2 history plus one ready C4 RLS for unpublished `0.6.0`, prepared by exact 0.5.0 in the derived two-file sparse view and validated in the complete graph.
- **Non-conforming:** ignore every rejected record without checking its lifecycle validity.
- **Non-conforming:** copy a hand-authored RLS into the repository and claim predecessor preparation.
- **Non-conforming:** omit an arbitrary artifact so old validation passes.
- **Non-conforming:** upgrade the root evaluator before publication.

## Explicitly unspecified decisions

Temporary directory names, internal dataclass names, and diagnostic presentation are delegated. Schema fields, selection rules, exact isolation, atomicity, lifecycle cardinality, and trust direction are fixed.

## Retirement amendment of 2026-08-27

On 2026-08-27, under `WO-REB-028` and `SPEC-REB-013`, the accountable owners retired the predecessor-view half of this contract. Rules 3 to 11 are withdrawn: `repository_tools/predecessor_preparation.py` and `scripts/prepare_predecessor_release.py` are deleted, no sparse preparation worktree is constructed for any evaluator, and no adapter imports predecessor-generated release bytes. Those rules are retained unchanged as the record of the one preparation they governed, `RLS-SEH-012`, and are no longer binding. The view evidence that preparation produced keeps its bytes and its bound `preparation_view_evidence_sha256`, which still verifies; the preparation itself is deliberately no longer re-derivable.

Rules 1, 2, 12 and 13 are unaffected and keep their full force. `REQ-REB-011`, which this specification also specifies, still requires them: only `ready` and `released` records claim a version, cardinality is at most one, a valid `rejected` record remains visible but inert history, and a released record admits no ready successor. Rule 12 now reads without its exception, because no predecessor view is available under any precondition. Rule 13's boundary is unchanged: nothing in the retained path created authority, and nothing that replaces it does either.

`REQ-REB-012`, the other requirement this specification specifies, is superseded by `REQ-REB-029` on the same date. Predecessor-to-successor assurance now comes from one mechanism only, the no-network `harnessctl rehearse-migration` rehearsal in `se_harness/governance_migration.py`.
