## Issue #101 preventive migration packet

The later approved `REQ-REB-016`, `REQ-REB-017`, `SPEC-REB-008`, `ARCH-REB-007`, `ADR-REB-007`, and `VER-REB-007` packet defines a complete predecessor-to-successor governance migration rehearsal. `WO-REB-018` is `in_progress` for its bounded implementation and local qualification. The packet adds evidence-only candidate behavior; it does not change the selected released root evaluator or absorb the lifecycle, production-view, or production-command work tracked separately by issues #103, #104, and #109.

`WO-REB-023` is `approved` under the same packet, for the first defect the packet's own success exposed. The candidate-evidence lane runs the `historical-0.5.0-to-0.6.0` scenario against a successor built from the candidate commit, so once the candidate was bumped to `0.7.0` the rehearsal refused it with `MIG211: successor version differs from the scenario` on both platforms, and the four downstream jobs including the deterministic integration package never ran. The refusal is `SPEC-REB-008` rule 4 working as specified; the configuration is what is wrong. Editing the historical scenario is forbidden — it is permanent regression history and the specification requires future successors to add scenario data instead — so the work order adds a scenario whose declared successor is the version the candidate builds, moves the pinned predecessor to the public `0.6.0` wheel, and adds the divergence test that makes the next version bump break a local test rather than a hosted gate. This is the first candidate bump since the rehearsal landed, and no release-sequence step told anyone to add a scenario. The work order also records a measurement taken while it was `draft`: the pair has no boundary the current contract can express, because the classification is a set difference over eight closed capability names that `0.6.0` already holds in full, and the boundary `MIG404` demands of a `historical-` scenario is hard-coded to the schema-3 and evaluator-evidence rule that `0.6.0` itself introduced. A real capability gap does exist — released `0.6.0` exposes no `qualify` — but it has no name in the vocabulary. So the scenario is either version-truthfully `compatible` or the contract gains a version, which is a governing amendment. The engineering owner approved the work order on 2026-08-25 with that measurement in front of them, in one act carrying four decisions: the `required` commit-bound verification classification stands and a `VREC` is owed; the scenario takes the version-truthful `compatible` route, so no governing artifact is amended and a new contract version naming the real capability is rejected for this work order rather than judged wrong; evidence retains under `WO-REB-023`'s own key as a routine reading of `VER-REB-007`, which is not amended; and the historical pair is dropped from the CI lane while staying byte-identical and exercised by the unit suite. The chosen route gives up the `MIG404` guard and the forced predecessor archive pin, so the work order pins the predecessor by digest anyway and asserts the `compatible` outcome in a test. Approval authorizes no start, no governing amendment, and no release act.

`WO-REB-023` is `in_progress` since 2026-08-25 and route A is implemented: `tests/fixtures/governance_migration/candidate-0.6.0-to-0.7.0.json` declares `0.6.0` to `0.7.0` with the predecessor holding all eight capabilities, so the pair classifies `compatible` with an empty affected-operation set; the lane runs that scenario against the public `0.6.0` wheel pinned by a freshly measured digest; the historical pair left the lane byte-identical and is still exercised by the unit suite; and five tests were added, including the coupling test that fails whenever the scenario the lane runs and the version the candidate builds diverge. That coupling has one consequence the implementation cannot decide for itself and does not hide: the scenario names `0.7.0`, so on any tree still declaring `0.6.0` — which includes `main` until the candidate bump merges — the coupling test and the hosted lane are red by design. The repair is therefore only complete in a tree that also carries the bump, which is `WO-RLS-011`'s candidate commit and a separate work order; the merge order is an owner decision and is put with the completion report rather than resolved by relaxing the assertion, which `SPEC-REB-008` rule 15 forbids.

## Issue #106 entry-point safety packet

Approved `REQ-REB-023` through `REQ-REB-026`, `SPEC-REB-011`, `ARCH-REB-010`, `ADR-REB-010`, and `VER-REB-010` define one declared interpreter-safety rule for every evaluator-identity boundary. `WO-REB-021` is `implemented` for its bounded local implementation and qualification, and `WO-REB-022` carries the bounded repair of one defect that work order shipped. Neither authorizes a release, a tag, a publication, a deployment, an external-policy change, or a root-evaluator adoption.

The packet answers RCA `RC-060-06`: a real POSIX virtual environment must be accepted through its lexical `bin/python` entry point, while linked parents, Windows junctions, checkout targets, unsafe aliases, non-terminal links, and escape attempts stay refused. Six boundaries in two runtimes currently decide this independently and disagree, so the correction places the rule in one declared document with one loader per runtime rather than patching the one site that fails on POSIX. The declaration is `se_harness/interpreter_safety.json` under schema `se-harness-interpreter-safety-v1`; it registers eight boundary identifiers across the six rule modules plus one delegating boundary. The canonical evaluator-evidence document, the runtime-identity schema identifier, existing bound digests, and root managed files are unchanged. The overlap with `WO-HBI-002` on `repository_tools/release_bootstrap.py` is disclosed in the work order for owner sequencing, and the engineering owner decided at approval that `WO-HBI-002` lands first.

Two owner amendments are recorded in the artifacts they change. `WO-REB-021` adds `se_harness/governance_migration_contract.json` to its execution scope for the six re-measured `implementation_sha256` values only. `SPEC-REB-011` rule 4 names the reparse-tag `stat` route as the junction predicate where `pathlib.Path.is_junction` is absent, because that predicate arrived in Python 3.12 while `requires-python` is `>=3.11` and every workflow lane pins 3.11; `VER-REB-010` was amended in the same act because it restated the same predicate in three places.

`WO-REB-022` repairs one defect in that implementation. The reparse-tag `stat` route does not exist on the pinned lane either: `IO_REPARSE_TAG_MOUNT_POINT` is published only where the platform defines it, so a Python 3.11 runtime off Windows had neither route and every boundary refused every interpreter with `EPS011`. The hosted `ubuntu` lane measured 33 failures and 38 errors on the `WO-REB-021` candidate; the Windows development lane cannot reach the defect, and the work order's retained evidence had disclosed exactly that gap. Rule 4 now gives the predicate a third route — whether the runtime's `os.stat_result` carries reparse members at all — so a runtime that observes no reparse information decides the predicate instead of refusing, while `EPS011` still refuses a runtime that can encounter a reparse point and cannot classify it. `REQ-REB-024` and `VER-REB-010` were amended in the same act. The defect cannot be repaired under `WO-REB-021`, because the work-order lifecycle admits only `verified` and `released` from `implemented`; that is why this is a separate work order, and why the candidate `VREC-REB-017` bound to the defective commit is superseded rather than re-pointed.

`WO-REB-024` (draft) repairs the second defect the 0.7.0 release exposed: `_derive_history` requires the whole catalog to hold exactly one rejected release record, where `SPEC-REB-005` rule 3 asks for exactly one rejected *predecessor-bootstrap* record. The first ordinary rejected record, `RLS-SEH-014`, breaks every predecessor-view derivation and with it the release qualification. The fix filters the selection to bootstrap records and touches no packaged byte.

`WO-REB-025` (draft) repairs the third defect the 0.7.0 release exposed: the last mile and the release-bound Pages build run the predecessor-view qualification unconditionally, where `REQ-REB-015` is conditional on a predecessor evaluator that cannot parse the bootstrap history. On the first ordinary record, `RLS-SEH-015`, the operation fails `PV001` and the dispatched publication stops in its first job. The fix exercises the view only when the record's contract declares a bootstrap tuple and retains an excluded observation otherwise; it touches no packaged byte.

`WO-REB-026` (draft) closes the gap `WO-REB-025` left in the Pages build: the Explorer generation step reads the view directory that only `qualify predecessor-view` creates, so for an ordinary record the release-bound demonstration failed after the tag, the GitHub Release and PyPI had succeeded (run `33020380987`). The exclusion branch now materializes the complete governance snapshot at the view path.

`REQ-REB-027`, `REQ-REB-028`, `SPEC-REB-012`, `ARCH-REB-011` with `ADR-REB-011`, `VER-REB-011` and `WO-REB-027` are drafted on the owner's 2026-08-27 direction after the rejected 0.7.0 adoption: the evaluator upgrade must be simple. The packet model of `REQ-REB-005` (the `[evaluator_upgrade]` work order, `MG007`) and the wheel-file requirement (`MG004`, and `RID022` on index installs) are retired; the installed evaluator's version and payload digest are its identity, the managed workflow passes from an index install, and the candidate-evidence lane selects the acceptance operation by the verifier's capability. `REQ-REB-005` is superseded under `WO-REB-027`.

`REQ-REB-029`, `SPEC-REB-013`, `ARCH-REB-012` with `ADR-REB-012`, `VER-REB-012` and `WO-REB-028` are drafted and approved on the owner's 2026-08-27 direction after [issue #190](https://github.com/mmzen/se_harness/issues/190): the predecessor-bootstrap release path is retired outright rather than repaired a fourth time. It was authored for one event, retaining the rejected `REL-SEH-008` / `RLS-SEH-009` pair while released 0.5.0 still had to judge the 0.6.0 release, and `REQ-REB-011` removed that cause in 0.6.0. 0.7.0 proved it: `RLS-SEH-014` was rejected and `RLS-SEH-015` released with no view at all, while the three defects `WO-REB-024`, `WO-REB-025` and `WO-REB-026` repaired all came from the same leftover assumption of a single rejected release record. Four `repository_tools` modules, four entry-point scripts, four test modules, the `predecessor-view` qualification operation and the workflow steps that selected a record for a view are deleted; `PV001` and `PV002` stay reserved. The six closed 0.6.0 artifacts keep their bytes and their hash-bound evidence digests, so that history stays verifiable and is deliberately no longer re-derivable. Predecessor-to-successor assurance comes from one mechanism only, `harnessctl rehearse-migration`. `REQ-REB-012` and `REQ-REB-015` are superseded and `SPEC-REB-007` with them; `SPEC-REB-003` and the predecessor-view rules of `SPEC-REB-005` are amended, keeping the rejected-succession rules `REQ-REB-010` and `REQ-REB-011` still require. The hash-locked managed validator is not edited: its two conditional bootstrap rules are inert, and retiring them with `REQ-REB-008` and `REQ-REB-010` needs a later work order and a release.
