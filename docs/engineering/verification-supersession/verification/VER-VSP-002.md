# Verification Contract: Verify state-aware VREC supersession provenance

## Independence

Tests assert observable record fields, lifecycle events, validation results, inspection queues, and no-write behavior. Expected metadata is declared independently rather than generated by the production transition helper. Legacy fixtures preserve their historical byte shape.

## Requirement-to-evidence matrix

| Requirement | Method | Case/evidence | Pass condition |
|---|---|---|---|
| REQ-VSP-008 | end-to-end command test | current ready record produced with preparation fields, eligible verified successor, supersession plan/apply | final graph validates; preparation is unchanged; supersession fields/event are exact; verification fields remain absent; source leaves the active queue |
| REQ-VSP-008 | validator matrix | current ready, verified, rejected, and superseded shapes | status-specific fields are required and forbidden exactly as specified; rejection behavior is unchanged |
| REQ-VSP-008 | legacy compatibility matrix | historical ready/superseded records without preparation fields and with legacy `verified_at` capture | records retain validity without added `verified_by`, preparation fields, or rewrites |
| REQ-VSP-008 | failure and atomicity | fabricated verification fields, partial preparation pair, ineligible successor, lost coverage, cycle, active RLS reference | each case fails deterministically before write or rolls back without residue |
| REQ-VSP-008 | distribution conformance | source package, canonical template, initialized repository, installed evaluator | the corrected validator behavior is identical across candidate source and an isolated installed candidate package |

## Acceptance scenarios

1. Capture a current ready VREC with the supported writer.
2. Establish one eligible verified successor covering the same work through supported lifecycle operations or an independently declared valid fixture.
3. Plan and apply the source `ready -> superseded` transition.
4. Confirm complete validation, exact lifecycle event consistency, and inspection queue removal.
5. Repeat direct validation with the preserved legacy superseded shape.

## Property and invariant tests

- Supersession never creates verification authority.
- Current preparation fields survive byte-for-byte through the transition.
- The only mutable fields are status, update date, supersession decision fields, successor relation, and lifecycle event.
- Current verified records still require decision timestamp and actor.
- Rejected and superseded remain semantically distinct.
- Legacy input is never rewritten by validation.

## Static and architecture checks

Confirm the writer emits preparation fields, the transition mutator emits only target-specific fields, and both direct and transition validation load the same packaged managed validator. Confirm no concrete VREC or released-root managed file enters the implementation diff.

## Security and privacy checks

Retain existing malicious successor, malformed timestamp, control-character actor, duplicate relation, cycle, evidence-path, and active-release-reference tests. Prove the generation discriminator cannot bypass candidate, evidence, coverage, type, status, or event checks.

## Performance and resilience checks

Run focused tests repeatedly and the complete suite. Exercise failed plan and failed apply no-write behavior. Confirm the constant-time field classification does not change graph complexity.

## Manual assessments

Review diagnostic wording to ensure it never says a superseded candidate was verified. Review the final diff and generated inspection output for clear separation of preparation, verification, and supersession.

## Evidence retention

Retain the exact issue reproduction, focused and full test commands, validator matrices, transition result/write set, formal graph and distribution checks, installed-candidate results, hashes where applicable, diff review, deviations, and residual risks under `docs/engineering/verification-supersession/evidence/WO-VSP-007-verification.md`.

## Residual uncertainty

Historical records do not carry an explicit schema-generation marker. Absence of preparation fields is therefore the compatibility discriminator; tests must prevent it from weakening current prepared records.
