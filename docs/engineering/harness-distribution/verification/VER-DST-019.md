# Verification Contract: Verify safe transactional artifact renumbering

## Independence

Expected behavior derives from `REQ-DST-061`, `SPEC-DST-019`, `ARCH-DST-012`, and the decision proposed by `ADR-DST-012`, not from implementation helper names or snapshots generated by the command under test. Disposable Git repositories contain independently authored artifact graphs, reference files, evidence bytes, hostile paths, and injected filesystem failures. Verification compares complete before/after inventories and hashes rather than accepting command success text as proof.

## Requirement-to-evidence matrix

| Requirement | Method | Case/evidence | Pass condition |
|---|---|---|---|
| `REQ-DST-061` explicit bounded mapping | CLI and API integration tests | single map, multi-map, reordered maps, missing/duplicate/chained/cyclic/type-mismatched maps | only complete one-to-one type-preserving mappings plan; order does not change semantic output |
| `REQ-DST-061` bounded repository repair | graph, text, and path fixtures | selected IDs, inbound/outbound relations, formal prose, source comments, tests, canonical/legacy filenames, evidence directories | every structured identity, relation, and planned path changes exactly once; free-form occurrences remain byte-identical and appear in the correct manual, evidence, or unsupported category |
| `REQ-DST-061` historical integrity | provenance and evidence fixtures | VREC/RLS reference, ready/terminal lifecycle, captured text and binary evidence | provenance involvement blocks all writes; eligible evidence paths move while every evidence content hash remains identical |
| `REQ-DST-061` transactional safety | phase-by-phase failure injection | replacement staging, first and later writes, path moves, postconditions, validator failure, rollback interruption | success is all-or-nothing; ordinary failures restore exactly; unresolved rollback is explicit and never reported as success |
| `REQ-DST-061` authority boundary | process/Git spies and output assertions | plan and apply modes | no fetch, ref update, add, commit, push, lifecycle transition, VREC/RLS mutation, allocation, or authority claim occurs |

## Acceptance scenarios

- Plan and apply one eligible draft artifact with inbound and outbound relations.
- Apply an explicitly mapped requirement, specification, architecture, ADR, verification contract, and work order whose map arguments arrive in several orders; resulting inventories and JSON are equivalent.
- Move a canonical artifact filename and a valid legacy artifact filename without moving unrelated legacy content.
- Rename `evidence/WO-MOK-010/`, filenames containing `WO-MOK-010`, and formal links to those paths while proving all evidence-file bytes and modes are unchanged.
- Preserve old identifiers printed inside `.txt`, `.json`, Markdown, and binary evidence while reporting bounded occurrence counts and hashes.
- Report exact identifiers in UTF-8, UTF-8-with-BOM, LF, CRLF, and CR free-form tracked text with correct one-based lines while leaving the complete files byte-identical.
- Reject substring and larger-token lookalikes such as four-digit suffixes, differently cased values, and another artifact namespace.
- Reject a selected artifact named by any verification or release record, including a `ready` record.
- Reject dirty staged, modified, untracked, merge, rebase, detached-without-HEAD, bare, and non-Git targets.
- Demonstrate that plan mode is byte-, path-, index-, ref-, and status-preserving.
- Demonstrate that apply output says `REPOSITORY REPAIR COMPLETE: no` (or schema-equivalent) whenever manual or unsupported references remain and uses resulting paths after mapped path moves.

## Property and invariant tests

- Mapping order and tracked enumeration order do not change normalized plans or JSON bytes.
- Every accepted plan is injective, type-preserving, acyclic, and destination-disjoint.
- Applying a successful plan leaves zero old identifiers in parsed `id` or typed-relation fields and accounts for every remaining occurrence in exactly one manual, preserved-evidence, or unsupported-content category.
- Unmapped artifact metadata, lifecycle state, owners, dates, statements, decisions, relations, and body bytes remain unchanged.
- Evidence content SHA-256, length, and mode are invariant across path moves.
- Free-form artifact bodies, documentation, source, and tests have identical bytes before and after apply, including encodings and line terminators.
- Successful apply Git status contains exactly the planned adds, deletes, renames, and modifications.
- A successfully rolled-back apply has the same `HEAD`, porcelain status, path set, modes, lengths, and SHA-256 inventory as before invocation.
- Repeated plan runs on unchanged input are byte-identical and write nothing.

## Static and architecture checks

- Assert CLI help, parser behavior, public JSON schema, error codes, and package entry point expose only the approved interface.
- Assert the implementation keeps inventory, planning, mutation, rollback, and postcondition responsibilities separated as required by `ARCH-DST-012`.
- Assert candidate and installed-package behavior agree and no runtime dependency is added.
- Assert command-reference documentation describes plan-by-default behavior, explicit mapping, manual hard-reference follow-up, evidence preservation, provenance refusal, and lack of allocation or commit authority.
- Run focused CLI, authoring, provenance, installer, standard-repository-lifecycle, integrity, and instruction-routing tests.
- Run the complete unit suite on Python 3.11 and the available local supported runtime.
- Run formal artifact validation, release-distribution validation, CLI help, `doctor`, phase-appropriate preflight, and final diff hygiene.

## Security and privacy checks

- Exercise traversal, absolute, drive, UNC, device, alternate-data-stream, reserved-name, trailing-dot/space, Unicode normalization, case-folding, symlink, junction, hard-link, non-directory-parent, and destination-collision cases on supported platforms.
- Supply Git paths and artifact text containing controls, shell metacharacters, option-like names, markup, quotes, separators, and command-like content; prove nothing is interpreted or executed.
- Exercise invalid UTF-8, embedded NUL, large files, large evidence trees, excessive mappings, excessive files/bytes, and oversized diagnostics.
- Patch subprocess and environment boundaries to prove Git receives argument arrays without shell evaluation and no repository hook, filter, attribute, Python module, template, or executable runs.
- Confirm human and JSON output never emits file bodies, environment values, credentials, unbounded evidence, unsafe terminal controls, or executable suggestions.
- Verify protected managed files and lock-owned content block unauthorized full-file rewriting.

## Performance and resilience checks

- Exercise at least 250 evidence files and 500 exact occurrences within documented capacity, with deterministic plan time and bounded memory/output.
- Inject failures before mutation and after every distinct write/move/postcondition phase.
- Exercise abrupt pre-commit transaction interruption through the supported recovery seam and prove the next invocation reports or completes recovery without overwriting unrelated content.
- Exercise Windows and POSIX path semantics where available, including case-insensitive destinations and cross-platform mode preservation expectations.

## Manual assessments

- Review a representative human plan and apply result for clarity about mappings, structured changes, manual hard-reference work, evidence preservation, blockers, validation, rollback, and authority.
- Review the manual-action list against a complete repository search; change or explicitly document each current hard reference before claiming repository repair complete, and confirm historical or unrelated prose was not silently rewritten.
- Review preserved captured output containing old identifiers and confirm the result is historically truthful and explainable from the report.
- Confirm the command remains simpler and narrower than allocation, ref scanning, PR comparison, or ledger proposals.

## Evidence retention

Retain owner authorization, start and review preflight manifests, exact changed paths, disposable fixture definitions, mapping matrices, manual/preserved/unsupported reference inventories and their dispositions, before/after and rollback inventories, evidence hashes, hostile-input results, failure-injection results, human/JSON samples, focused and full test commands/counts, Python versions, validation and doctor summaries, package/CLI/documentation parity, diff review, deviations, residual risks, and unperformed authority actions at `docs/engineering/harness-distribution/evidence/WO-DST-019-verification.md`.

## Residual uncertainty

The command cannot see identifiers selected in another unshared checkout or guarantee that a caller chose a globally unused replacement. It cannot decide whether free-form text is a current hard reference, historical narrative, or unrelated content; accountable reviewers must disposition the reported list. Filesystem recovery semantics vary across platforms, and process termination at an operating-system boundary can require explicit recovery on the next invocation. Preserved evidence intentionally contains historical identifiers, so reviewers must use path context and retained command output to interpret them.
