# Commit complete lifecycle results atomically

## In plain words

A lifecycle action can change several records and evidence files. The service
must retain the whole result together. Retrying after a lost reply must not
repeat an accepted action.

## Why

Phase 2's single-draft mutation is insufficient for decision effects, handoff
evidence, and generated verification or release records.

## Behavior and acceptance

1. Preview identifies the exact proposed changes and their input versions.
   Apply rejects changed inputs; a prior preview does not bypass current gates.
2. One accepted action stores the complete generated byte set, immutable
   revisions, selected heads and operation receipt in one transaction.
3. No effect outside the closed operation's permitted output set is accepted.
4. Concurrent incompatible writes have one winner. The losing request leaves
   no partial records, evidence or receipt claiming success.
5. Repeating a key with identical inputs returns the retained result. Reusing
   it with different inputs fails. An uncertain reply is reconciled by receipt,
   including after service restart.

## Examples

**Normal:** A test verification capture writes its record and evaluator sidecar.
Both become visible with one receipt. A retry returns their same hashes.

**Failure:** A forced failure between staging the record and its sidecar leaves
the graph at its previous version. No incomplete verification record is visible.
