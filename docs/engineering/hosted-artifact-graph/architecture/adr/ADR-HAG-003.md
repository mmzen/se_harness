# Use ordinary Git projections for the lifecycle rehearsal

## Status

Draft for approval. The design below is the proposed decision; no human
architecture approval or implementation authority has been recorded.

## Context and drivers

DEC-HAG-004 keeps Git authoritative. The service must exercise lifecycle and
verification behavior while authentication and database ACL work are deferred.
Released evaluator 0.22.1 captures a clean Git candidate and does not expose a
native hosted-baseline argument. Its record bytes and policy must remain intact.

## Considered options

| Option | Benefits | Cost and limitation |
| --- | --- | --- |
| Keep only Phase 2 draft reads/writes | No new persistence or provenance behavior | Cannot exercise approval, work completion, verification or release-record preparation |
| Add native hosted candidate-plus-baseline provenance to the evaluator now | Could support a future real authority cutover | Requires new evaluator policy, schema, release and adoption; exceeds the selected test-copy outcome |
| Use disposable ordinary Git projections and atomic complete-result storage | Reuses released commands and permits a full private rehearsal | Must retain test Git history, distinguish test commits and export complete evidence |

## Decision

Use the third option. Materialize the selected hosted inputs into an ordinary
disposable Git repository, invoke released 0.22.1, and atomically store the entire
permitted output set. Preserve its Git objects and exact generated bytes.

The test-projection commit is the candidate assessed by a test VREC. It is not
the implementation commit assessed by the real repository's VREC. Export labels
and manifests preserve that distinction. The graph does not become authoritative
for real work, even when a rehearsal record reaches `verified` or `released`.

## Consequences

- Reuse one service, one store, existing transactions, receipts and evaluator
  isolation. Avoid a second lifecycle policy or a new orchestration service.
- Extend storage to complete multi-file outputs, including opaque evidence and
  required Git objects. Account for their retention and export size.
- Test capture remains bounded by the released file-based evaluator. A genuine
  incompatibility blocks the affected operation and requires a separate proposal.
- Use a fresh pilot volume; migration of Phase 2 volumes is not promised.
- Keep existing sandbox controls and RISK-HAG-001. This does not resolve identity
  spoofing or database ACL risk and permits no public/production authority.
- A future real cutover needs a separate architecture/authority decision and
  its own security, provenance, release and adoption work.

## Validation

VER-HAG-006 compares hosted and independent file-based lifecycle results, forces
partial-write and stale-input failures, and reconstructs exported history. These
tests assess the proposed architecture without treating simulated decisions as
real human approvals.
