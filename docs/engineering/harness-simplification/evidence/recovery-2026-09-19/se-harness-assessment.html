01 / Assessment

The records are checked more strongly than the decisions behind them

SE Harness helps an AI agent follow a software development process. It records what should be built, who approved the work, what was tested, and whether the result may be released.

It does a useful job of checking that these records fit together. But it often trusts what someone writes in them. That leaves a gap between “the record says this happened” and “the system has proof that it happened.”

In separate test projects, the released checker accepted:

  • An approval entered under a name that was not listed as the record’s owner.
  • An evidence file that plainly said the required tests had not run.
  • A work item marked complete after another check had rejected an unapproved file change.

The harness therefore works best when the owner trusts the agent to follow the process honestly. It does not, by itself, stop an agent from skipping steps or writing its own claims of approval.

These findings show weaknesses in the checks. They do not show that real approvals were forged or real releases were faulty.

A few terms used in this report
AI agent
An AI system that can read files, change code and run commands.
Repository
The project’s files and their saved change history.
Git
The tool that saves versions of the project and tracks which files changed. GitHub hosts projects that use it.
Checker
The harness program that reads the records and applies its rules. Its command name is harnessctl.
Gate
A check that must pass before the next step is allowed.
Evidence
Saved observations, such as test commands and their results, used to judge the work.
Commit
A saved version of the project, with a unique identifier.
Pull request
A proposal to add changes to the shared project. Accepting those changes is called merging.
CI
Automatic jobs, often run by GitHub, that check proposed changes.
Plugin
An add-on that gives the AI application extra instructions or tools.

02 / The intended workflow

From a clear request to an approved release

The harness asks the team to keep connected records. A requirement explains what the software must do. A work order says what may be changed. A review record links the evidence to the exact saved version being reviewed. The connections must be written into the records; a chat message or filename is not enough. [S01] [S02]

  1. Read the rules

    The agent reads the project instructions and the documents needed for the selected work. It uses the checker version chosen by the project and checks that protected rules have not been changed.

  2. Define and approve the work

    The team records the expected result, the design where needed, and how success will be tested. The responsible owners approve those parts. An engineering owner approves a work order with clear limits.

  3. Start and carry out the approved work

    The agent confirms that its permission still applies, marks the work as started, makes the allowed changes, runs the required checks and saves their results. It should not need fresh permission for every ordinary step already covered by the approval.

  4. Check the finished work

    A handoff check reviews the work before it is marked complete. It should check the changed files and the saved evidence. Finished coding is not the same as independent approval of the result.

  5. Review the evidence

    When the work requires it, the agent prepares a review record for an exact saved version. The person responsible for assurance—judging whether the evidence supports the result—then approves or rejects that record.

  6. Decide how to deliver it

    Adding the changes to the shared project and preparing a release are separate choices. A release owner makes the release decision. Publishing or deploying the software still needs permission for that specific action.

Preparing a review or release record does not approve it. Approving one record does not silently approve the others. The harness also allows rejection and, in some cases, replacement of an earlier review. [S03] [S04] [S17]

A review or release record is saved after the version it describes. Otherwise, it would have to include its own final identifier before that identifier exists.

03 / What stops mistakes

A written rule is not the same as a blocking check

The harness uses three kinds of control. Their strength is different.

ControlWhat it doesIts limit
InstructionsTell the agent what to read, when to stop and whose approval is needed.The agent must remember and follow them. The reviewed plugin does not automatically check every tool action.
Harness checksCheck records, allowed status changes, files and saved version identifiers.They run when called. Some inputs are claims supplied by the same agent they are meant to guide.
Server rulesCan block a merge or publication even if local instructions are ignored.Only the rules actually enabled on the server apply. Required jobs and reviewer settings matter.

The strongest checks concern facts a program can compare directly: which files changed, whether record IDs match, and whether protected file content has changed. The weaker checks concern human claims: who really approved something, whether the right tests passed, and whether a reviewer was independent. [S05] [S07] [S08] [S11] [S16] [S17] [S18]

What a passing result does—and does not—tell you
  • Matching record links do not prove that the code meets the written requirement.
  • Changing only approved files does not prove that the changes have the approved purpose.
  • An evidence file being present does not prove that its tests passed.
  • A saved version identifier tells you which software is being discussed. It does not tell you whether that software is good enough.
  • A healthy checker installation does not prove that GitHub will run all necessary checks or require an independent reviewer.

04 / The findings

Ten places where the process can break down

High means the gap can undermine an important approval or completion claim. Medium means it can cause confusion or weaken reliability. These are review priorities, not formal security scores.

“Shown in tests” means the behavior happened in a separate test project using the checker’s normal rules. “Observed” means it was found in code, instructions or GitHub settings. Possible effects on an AI agent are explained as risks, not measured failure rates.

F1 High · Shown in tests

A typed name can stand in for real approval

What happened: a draft record listed one owner. The checker still approved it when given a different, unrelated name as the person making the decision.

The checker accepted the name as text. It did not prove that the named person was present or had the right to approve this record. Review and release records have some extra owner checks, but their owner lists are also editable project content. [S05] [S06] [S15]

Why it matters: an agent may copy a suggested command containing an owner’s name and mistake that name for permission. The plugin warns against this, but the command itself can still succeed. [S17]

Improve it: obtain important approvals through a protected channel that confirms who approved what. Keep the display name separate from proof of permission. If a name is only a user-supplied claim, say so.

F2 High · Shown in tests

The approved file list can stay the same while the purpose changes

What happened: an approval written directly into a test work order was accepted. The test project did not even need saved Git history for that approval to be recognized. Adding new instructions to the work order, while keeping the approved file list unchanged, still allowed the handoff check to pass.

The current approval check compares file lists. It does not preserve proof of the full work description and design that the owner originally reviewed. Decision-history checks mainly test whether the entries fit together; that is not the same as proving they have never been rewritten. [S06] [S07]

Why it matters: “you may edit these files” is weaker than “you may make this specific change.” An agent could change the meaning of the task while keeping the same file list.

Improve it: save the reviewed work description and design version with the approval. Define which changes need renewed approval. Normal coding within the original task should still be allowed without repeated requests.

F3 High · Shown in two tests

A failed or old test report can still count as available evidence

What happened: a handoff passed with an evidence file that said:

FAIL: the required tests did not run; there is no passing test result.

For this kind of evidence file, the check looks for a readable, nonempty file. It does not check whether the text records a successful test. [S08]

A second test changed the code, then ran a handoff check. The checker updated the old report’s label to match the new code. It kept the failure text unchanged and still passed. It did not rerun the tests. [S09] [S10]

Why it matters: a current-looking label can make old evidence seem fresh. The label proves that the report was linked to the new code, not that anyone tested that code.

Improve it: keep the actual test run separate from the file attached as evidence. Record which version was tested, which test ran, and its result. Updating an attachment must not make an old test result count as a new one.

A useful feature to build on

The development version already has a way to run a supplied test command against a saved candidate version. That can provide stronger evidence. The project still needs to define which tests are required; running an easy but irrelevant command would not be enough. [S14]

F4 High · Shown in tests

Work can be marked complete after its handoff fails

What happened: the test changed one approved file and one unapproved file. A check that read the real changes from Git correctly rejected the handoff. The separate command to mark the work as implemented then succeeded.

The completion command does not perform the full file-change check. It also does not require a successful, up-to-date handoff result. [S10] [S11]

Why it matters: the process says “stop,” but another route still lets the agent record “done.” A later GitHub check may catch the bad change, yet the local completion record is already misleading.

Improve it: make completion depend on the full check for the current changes. Missing, failed or outdated handoff results must block completion.

F5 High · Observed in GitHub settings

The shared project does not require all the review and test steps

What was found: on 16 September 2026, the main branch required a pull request and a check named validate. It required zero approving reviews. The separate jobs that test the proposed software were not listed as required checks.

The required validate job checks harness records and allowed changes. It is not the full software test suite. The server settings therefore do not prove that every merged change passed those tests or received an independent review. This is a finding about settings, not evidence of a bad merge. [S12] [S13] [S18]

Publishing to PyPI, the Python package service, does require a reviewer. But the setting allows self-review, so that protection alone does not guarantee a second person checked the release. [S19]

Improve it: make the required test jobs and reviewer rules match the process the project promises. If one owner is allowed to play several roles, describe that clearly.

Other settings recorded during the review

The main-branch rules also blocked deletion and forced rewriting of history. They did not require a code-owner review, approval of the latest push, removal of old approvals after a new push, or strict up-to-date checks. An allowed repository role could bypass rules through a pull request. The separate release and plugin-marketplace rulesets were disabled.

PyPI publishing was allowed from main. These are dated observations; the settings may change. [S18] [S19]

F6 High if the agent is not trusted; otherwise medium · Shown in tests

A healthy installation does not mean its automatic checks are useful

What happened: the test replaced the supplied GitHub checking job with one that only printed “pass.” The harness installation-health command, called doctor, still passed.

This GitHub job is meant to be editable. The health check confirms that the file is present, rather than proving that it still runs the expected checks. By contrast, an unauthorized edit to a protected harness rule file was correctly rejected. [S03] [S12] [S16]

Why it matters: if an agent can weaken the checking job, requiring a successful job with the same name may not protect the project.

Improve it: protect changes to the checking jobs, or run the trusted checks from a place the proposed change cannot replace. Report installation health separately from the strength of GitHub’s protections.

F7 High for clear instructions · Observed in the guides

The guides disagree about who may start and finish work

What was found: one rule says that approving a work order gives the executor permission to start, code, check and record completion without asking again. Another part of the workflow asks for an explicit start decision and says the engineering owner may mark the work implemented. [S04]

A “start decision” might simply mean the executor records that work has started. The guide does not make this clear. The different descriptions of who records completion are harder to reconcile.

Why it matters: an agent may keep asking for permission it already has. Or it may read a broad permission as covering a decision reserved for an owner.

Improve it: use one short table that states who may perform each action and whether existing approval is enough. Keep the guides and program rules aligned.

F8 Medium · Shown in both checker versions

A readiness check and the next command can disagree

What happened: an unrelated draft record was missing its owner. The check for completing the selected work order passed. Planning that same completion then failed because the planner rejected the unrelated record error. [S05] [S10]

Why it matters: the agent is told that its next step is acceptable, then refused for a different reason. This can send it into unrelated repairs and expand the task beyond what was approved.

Improve it: use the same rules for what blocks a selected task in the check, the plan and the final action. Some errors really affect the whole project; those exceptions should be named clearly.

F9 Medium · Observed and partly shown in tests

The word “check” promises more than some checks do

What was found: the same command name covers several different operations:

  • Showing the current stage and suggested next step, without testing whether the required checks pass.
  • Checking the file list, without granting permission to do the work.
  • Checking a handoff and sometimes updating saved evidence files.

Why it matters: an agent may report “the check passed” when it only received a next-step suggestion. It may also assume that a check only reads files. A gate with “assurance decision” in its name can sound as though independent review has happened, even though its automatic checks mainly examine records. [S09] [S10] [S11] [S20]

Improve it: state the limit directly in each result: “Next-step suggestion only,” “Evidence found; test success not checked,” or “These files were updated.” Name exactly what a passing result proves.

F10 Medium · Reading size measured; agent risk inferred

The agent has a lot to remember, across several versions of the rules

What was found: the nine main instruction and policy files contained about 95 KB of text. One work order’s required reading covered 21 files and about 151 KB. The project contained 1,652 formal records.

The agent must read rules at the start, read more for the selected stage, and reread important context after a long conversation is shortened. Rules also appear in several places. The project uses released checker version 0.18.0 while the development code says 0.19.0. Keeping those separate protects the checker, but makes it easier to run a plausible command with the wrong version. [S01] [S03] [S17]

Similar record names add to the burden: a test plan is not a test result, and a prepared release record is not release approval. Two agents can also choose the same next record number. Checking existing branches does not reserve that number.

Improve it: give the agent a short brief for its current stage: the rules it must follow, what is already approved, what remains undecided, and the next action. Link to the full documents. Add a reliable way for parallel agents to reserve record IDs.

05 / What works well

There are useful controls worth keeping

  • Connected records make the reasoning visible. The team can trace work back to requirements and decisions.
  • The released checker is separate from the code being developed. This helps stop a change from quietly redefining its own checks.
  • Some important failures are caught. The tests caught an unapproved file change when Git supplied the real file list. They also caught an edit to a protected rule file.
  • Preparation and approval are separate. Creating a review or release record does not automatically approve it or change all related records.
  • Saved version links are useful. They help reviewers establish which software and evidence a decision refers to.
  • The project tests its behavior. The focused run completed 158 tests, with one skipped and no failures. The project also recognizes that replaying commands is different from testing how an AI agent chooses its actions.

The plugin openly states that it does not intercept every action. The improvement needed is to make the strength of each result equally clear. [S01] [S11] [S14] [S16] [S17] [S21]

06 / What to fix first

Make “approved,” “tested” and “complete” more reliable

OrderChangeHow to know it works
FirstRequire the full handoff before completion.The failed-handoff example can no longer end with the work marked complete.
FirstCheck actual test runs, not just attached files.A missing, failed or old test stays unproven when its attachment is updated.
FirstRequire the right GitHub jobs and reviews.The normal merge route blocks changes that lack the required tests or review.
NextConfirm who approved the work and preserve what they reviewed.Editing a record cannot create permission or silently broaden it.
NextProtect the automatic checking jobs.A replacement job that merely prints “pass” cannot satisfy the trusted check.
NextMake guides and commands agree.The agent gets the same answer about permission and blockers at each step.
ThenShorten the reading brief and reserve record numbers.Fresh agents can find the right next action; parallel agents get different IDs.

“First” means before presenting these checks as strong barriers against incorrect agent actions. It does not mean all project work must stop.

Decide how much the system is allowed to trust the agent

If the agent is trusted, the harness can organize its work, catch mistakes and preserve a useful history. Claims entered by the agent should still be labelled as claims.

If the agent must be constrained, it cannot control its own approval, evidence and checker. Some protection must sit outside the files and settings it can edit—for example, protected reviews and server-run checks.

The project owner may remain the trusted final authority. If that owner can change every protection, the harness cannot also claim to independently constrain that same owner.

Test the decisions an agent makes

Keep the failure examples in this report as repeatable tests. Also test a fresh agent, an agent resuming a shortened conversation, two agents working at once, an old approval applied to changed work, and a command whose success is uncertain. Record what the agent actually did. A script that simply replays expected commands cannot show that an AI agent will choose them correctly. [S21]

07 / What was tested

The strongest findings were reproduced with the released checker

The review used the project’s released checker, version 0.18.0, and examined the development code, version 0.19.0. Experiments ran in separate, disposable projects. The checker’s approval and evidence checks were not turned off. No project settings, release records or repository code were changed.

The development-code checks reproduced the matching planning and check results. Changes to record status in these experiments were applied only through the released checker.

A separate focused run covered 158 tests: one skipped, no failures, in about 74 seconds. It was not the full test suite. The review did not try a real publication or attempt to merge around GitHub’s protections.

The GitHub findings describe settings observed on 16 September 2026. They were not rechecked for this plain-language edition. Actual behavior by future agents, and every possible route to publishing software, were not measured.

More detail about the test method

The synthetic records were created with helpers from the repository’s test suite. No real owner approval was claimed. The first trial used an old work-order ID format and was correctly refused. The corrected run used WO-AUD-001 and started with zero record-validation errors. Both the exploratory and corrected results were kept.

The focused test files were test_workflow_execution, test_workflow_compliance, test_authoring_gate, test_instruction_architecture and test_workflow_documentation_contract. Some existing unit tests replace parts of the system with test substitutes. The separate reproduction experiments did not replace the approval, evidence or permission checks.

The review checked GitHub’s effective branch rules, not only the older protection API. The older API reported no protection, but an active ruleset did protect the main branch. It would be wrong to say the branch had no protection at all.

08 / Questions to resolve

Six decisions would make the design clearer

  1. Is the harness helping a trusted agent, or stopping an agent from giving itself permission?
  2. What proof is required before work can be called complete, verified or released?
  3. Why should updating a report’s label make old test results count for changed code?
  4. Exactly what did the owner approve, and what changes require a new decision?
  5. What must GitHub refuse even if the agent skips every local instruction?
  6. Can a fresh agent find the right next action without reading conflicting guides or learning through repeated refusals?

Answering these questions and fixing the first six findings would strengthen the existing workflow more than adding more record types or instructions.
