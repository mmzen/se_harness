01 / Recommendation

Keep the harness. Repair the meaning of its results.

Use the harness to guide a trusted agent and catch mistakes. Use protected GitHub checks and human review to control what enters the shared project and what gets published.

This is one workflow with clear limits. It does not need a second operating mode, a new approval service, or a larger set of records.

The rule to design around: a file being present means “attached”; a successful test run means “tested”; a recorded name means “claimed by”; and a real owner decision means “approved.” The system should keep these meanings separate.

A normal task should still move from approval to implementation without repeated permission requests. Preparing a review or release record should still be allowed under the existing work approval. The actual review and release decisions remain with their owners.

Scope: this is a proposal, not an implementation or a formal lifecycle result. It uses the September 16 findings. Current code and GitHub settings must be checked before applying the repairs; they have not been re-audited for this plan.

02 / KISS

Fix each problem at the smallest useful place

The repository’s simplicity policy asks for the least complex design that meets the agreed need. It also counts the work imposed on users and maintainers. A shorter implementation is not simpler if it creates repeated approvals or manual checking.

  • Reuse existing parts. Improve the current evidence capture, handoff checks, workflow result and GitHub jobs.
  • Put each rule in one place. Handoff and completion should call the same checks. Guides should point to one short explanation.
  • Keep local work local. Starting or continuing an approved task should not depend on a live CI run or an unrelated draft record.
  • Preserve useful work. Keep valid results for unchanged inputs. Rerun affected tests when behavior changes.
  • Remove obsolete rules with their tests. A fix is incomplete if the old guide still asks for the opposite behavior.

For this recovery, defer a custom identity system, signed receipts, an approval database, a policy-generation framework, an ID-allocation service, and a new dashboard. No separate KISS approval or score is needed.

04 / The repairs

A concrete change and a clear test for each gap

Repair 1 · Findings F3 and F9 · Owner: harness maintainer

Report what the evidence actually proves

Change: stop a handoff check from updating an old report to look newly tested. Checking readiness should read the evidence; creating or updating evidence should be an explicit capture action.

Reuse the existing test-capture path. Keep the saved software version, test command, result and output reference together. Use the current record format where it already supports those facts. Add only the missing information.

The existing verification plan says which checks matter. A test that was required but never ran stays “not run.” A failed test stays “failed.” An attached document stays “attached” until its relevant contents have been assessed. A manual inspection can still count when the plan calls for it; it needs the responsible reviewer’s conclusion.

The result should say whether it merely suggests a next step, checks readiness, or changes files. Reuse the existing output fields and add a plain sentence where needed. A summary such as “Evidence attached; test outcome not assessed” is useful even when the attachment itself is valid.

Reuse rule: an unchanged result keeps its original tested version. Reuse it when the relevant inputs are demonstrably unchanged. If that cannot be established, rerun the affected check. Never relabel old output as a new run.

Done when: the F3 failure report and stale-report examples no longer satisfy a required successful-test check. A read-only check leaves files unchanged. A real successful capture still works. A harmless notes edit does not force a full test rerun.

This improves correctness; a locally writable test record is still not independent proof. Protected CI supplies that stronger check at integration.

Repair 2 · Findings F4 and F8 · Owner: harness maintainer

Give handoff and completion the same answer

Change: the command that marks work implemented must run the same current scope and evidence checks as the handoff. Share the existing checking code instead of maintaining a weaker second path.

Use Git to obtain the real changed files against the agreed starting version. Include pending edits when the operation supports them. Use the same baseline throughout the task; choosing a later starting point must not hide earlier changes. If the command lacks the context it needs, refuse completion and name the missing input.

Rerun the cheap checks immediately before changing state. Do not build a new system of stored “handoff passed” certificates. Do not rerun expensive tests just because completion was requested; Repair 1 determines whether the existing results still apply.

Use one rule for which errors block the selected task. Errors in its records, dependencies, or shared integrity block it. An unrelated incomplete draft does not. Preview, planning and applying the change should use this same rule.

Done when: the F4 out-of-scope edit blocks both handoff and direct completion. A new relevant edit after a passing handoff is checked again. The F8 unrelated draft no longer gives different answers in preview and apply. A valid task still completes normally.

“Implemented” means the agreed completion checks passed. It still does not mean independent assurance or permission to release.

Repair 3 · Findings F1, F2, F5 and F6 · Owner: repository owner, with the responsible reviewer

Use GitHub to protect the shared project

Change: require the existing jobs that actually test acceptance, alongside the harness validation job. Select their real status names after inspecting the current workflow. Do not duplicate the candidate test pipeline.

Require a fresh human approval for the version being merged. Review changes to workflow files, checker selection, ownership rules and approval records as control changes. An edit that replaces checking with “print pass” must not merge through the ordinary route.

Use existing review and ownership features. Check bypass permissions and keep routine agent credentials from changing protection rules or bypassing them. Apply the same principle to each publishing route the project actually uses.

For approvals: a typed actor name remains a recorded claim. Where an owner decision is required, retain a reference to the actual decision and the reviewed version in the existing record. At review, compare the work description, allowed paths and governing requirements with that version. Editing the record cannot supply the missing human decision.

Normal coding inside the approved task reuses its approval. A changed purpose, wider scope, weaker acceptance rule or changed governing requirement needs an amendment decision. Use the existing approval step for that amendment; do not require a fresh approval for every implementation edit.

Done when: a controlled test change cannot merge with missing tests, missing current review, or an unapproved change to the checking workflow. A broadened work description is sent back for approval. A local actor label is never presented as authenticated permission.

Limit: human review of an editable workflow is an owner-controlled safeguard. It is not an independent guarantee that the expected job ran. If stronger prevention is an agreed need, place the required checking entry point outside the proposed change’s control using supported GitHub features. Verify that route before claiming the gap is closed.

If only one human can review, say “owner-reviewed.” Do not call that independent assurance or invent a second identity. Independence needs a second qualified person; the plan cannot create one.

Repair 4 · Findings F7, F9 and F10 · Owner: workflow and plugin maintainer

Give the agent one short, consistent route

Change: edit the existing operating card and conflicting guide passages. Keep one small table for each action: who may do it, which existing approval covers it, and whether it needs a new decision. Remove duplicate explanations rather than adding another policy document.

Read the task → carry out approved work → capture results → check completion → request only the decisions still needed.

Put a short task brief at the top of the existing workflow result: selected work, governing checker version, allowed next action, blockers and any decision still needed. Link to the full sources. Keep the requirement and acceptance details that affect this task; shorten repeated policy text.

Clearly distinguish starting work from asking for permission to start. The approved executor can start, implement and record completion after passing checks. Preparing a review or release record does not approve it.

For concurrent agents: use the existing coordinator to assign non-overlapping blocks of record numbers once per active task, recorded in the current task allocation. Confirm the blocks against the shared project and active allocations. Keep duplicate detection before merge. Do not build an allocation service unless this simple arrangement proves inadequate.

Done when: an observed fresh-agent walkthrough and a resumed-agent walkthrough both use the right checker, complete routine approved steps without unnecessary permission requests, and stop at the real review decision. Two concurrent tasks receive different record numbers.

Use the existing agent acceptance setup. Scripted command tests alone cannot show that an agent understands the instructions. Number blocks are a coordination rule, not a guarantee for uncoordinated writers.

05 / Adoption

Prove the fixes, then adopt them normally

  1. Confirm the starting point. Recheck the current code and effective GitHub settings. Keep only findings still present. Reuse the saved reproduction cases.
  2. Test both refusal and success. Each code repair needs its observed failure example and a valid task that still passes. Include an unchanged-evidence reuse case. Use existing test files; avoid a new test framework.
  3. Run the required project checks. Focused checks support each patch. Run the repository’s required regression and package checks before accepting the combined change, using the existing CI route.
  4. Release and upgrade through the current process. Candidate code does not change an installed checker. Publish only under the existing release authority, then explicitly upgrade projects. Reconcile editable guides and CI files; the normal upgrade may preserve them.
  5. Keep history accurate. Preserve old approvals, review records and test evidence. For current unfinished work, missing or stale evidence stays unassessed until the relevant checks run. Do not rewrite old reports to manufacture compliance.

Stop condition for the recovery: all applicable acceptance examples pass on the installed released version; the ordinary task remains simple; and the remaining trust limits are stated plainly. Do not expand into a wider harness redesign.

If adoption fails, use the existing upgrade or rollback route and retain the failure evidence. Do not solve the failure by turning off required checks.

07 / Basis and sources

Grounded in the assessment and existing KISS work

  • Plain-language assessment — all ten findings, evidence and source links.
  • Saved assessment evidence — the original reproduction material.
  • Design simplicity policy — least complex adequate solution; no extra KISS artifact, score or approval.
  • Accepted KISS simplifications — local progress, evidence reuse, existing release jobs, and no repeated routine permission.
  • How the simplicity policy is adopted — normal release and explicit project upgrade.

The recommended repairs are design proposals. Their acceptance examples have not been run against a repaired product. Code links refer to the assessed commit, not to today’s main branch.
