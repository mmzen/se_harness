# Verification Contract: Independent evidence for authenticated decision records

## Independence

Expected behaviour derives from `REQ-ECP-008` and the `ECP-DEC-` rules of
`SPEC-ECP-004`, read against `ARCH-ECP-001` and the proposed outcome of
`ADR-ECP-003`. Test identities are generated by the test: a throwaway
signing key and a fixture identity source mapping signers to roles taken from
`DECISION_RIGHTS.md`. No accepted record in the fixtures is produced by the
candidate; each is written by hand from the record schema in the
specification.

## Requirement-to-evidence matrix

| Requirement | Method | Case/evidence | Pass condition |
|---|---|---|---|
| `REQ-ECP-008` decisions are authenticated records | test: `transition --apply` with a valid record; with a free-text `--decision`; with a record whose signer is unknown; with a verified signer whose role lacks the right; with a tampered record | fixture identity source; `DR-WO-START` on an approved work order | the transition applies only for the record whose signature verifies against the identity source and whose role holds the decision right; every other case is refused before any file is written, with a coded diagnostic naming the record, the decision right, and the failing condition; free-text actors are refused (today they pass a 128-character length check only, `se_harness/workflow.py:606`) |

## Acceptance scenarios

### Scenario 1: a valid record applies

Sign a record `{artifact, decision_right, outcome, reason, signer}` with the
fixture key of a signer mapped to `engineering-owner`. Run
`transition --apply --decision-record <path>`. Assert the lifecycle event
is appended and names the verified signer identity.

### Scenario 2: failure path, wrong role

Sign the same record with a signer mapped to `assurance-owner`. Assert
refusal naming `DR-WO-START` and the role, and that the artifact bytes are
unchanged.

### Scenario 3: failure path, unknown signer

Sign with a key absent from the identity source. Assert refusal and no
write.

### Scenario 4: failure path, tampered body

Alter `outcome` after signing. Assert signature verification fails and no
write.

### Scenario 5: failure path, legacy free text

Run `transition --apply --decision WO=engineering-owner`. Assert refusal
with a diagnostic pointing to `--decision-record`.

### Scenario 6: CI actor source

With the identity source configured to `GITHUB_ACTOR`, run in an environment
carrying an actor mapped to a role. Assert acceptance; with an unmapped
actor, assert refusal.

## Property and invariant tests

- For every decision right in `DECISION_RIGHTS.md` and every role, the
  transition is accepted exactly when the table grants the right.
- A record is accepted at most once per artifact and lifecycle edge; a
  replayed record after the edge is refused.

## Static and architecture checks

- `--decision` with an `ID=ACTOR` value is no longer a required argument of
  `transition` (`se_harness/cli.py:1037` today).
- The record parser lives in one module, `se_harness/decision_record.py`,
  and `workflow.py` imports it rather than re-implementing it.

## Security and privacy checks

- Private keys never appear in evidence; the evidence records public keys
  and fingerprints only.
- A record with a signer identity longer than the configured bound or
  containing control characters is refused.
- The identity source is read from the repository configuration path only;
  an environment-supplied path is ignored.

## Performance and resilience checks

- Verification of one record completes within one second on both platforms.

## Manual assessments

The assurance owner reads one refused-transition diagnostic per failure
scenario and confirms that each names a cause a human can act on.

## Evidence retention

Under `docs/engineering/execution-control-plane/evidence/<WO-ID>/`: the
fixture identity source, public fingerprints, each record and its verdict,
the refused-transition diagnostics, and per-platform test figures.

## Pass criteria

Every deterministic test passes on Linux and on Windows, figures labelled per
platform. Graph and integrity readings are taken with the exact released
evaluator, se-harness 0.7.1, installed outside the checkout; the candidate's
`transition` is exercised only against temporary repositories, never against
this repository's artifacts.

## Residual uncertainty

Strength of the identity source is a deployment choice; the contract proves
that an unverified or unauthorized record cannot apply, not that a given
identity source is hard to forge.
