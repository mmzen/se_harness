**Spec Kit versus se_harness — assessment of current source, 14 September 2026**

**Spec Kit is the stronger general-purpose system for turning an idea into agent-executed implementation. se_harness is the stronger system for governing the resulting engineering change and its verification/release evidence.** Their capabilities overlap, but their strongest mechanisms serve different purposes.

For se_harness, the most useful direction is to retain its deterministic governance core and improve the authoring and execution experience around it. Spec Kit is a useful reference for that experience and potentially an integration surface. Replacing se_harness with Spec Kit would lose substantial lifecycle and provenance functionality.

This is an engineering assessment, not a formal harness lifecycle decision. Scores describe the inspected implementation and developer experience. They do not measure coding-model accuracy, productivity, defect rates, security certification, or actual enforcement of GitHub settings.

I interpreted “current code base” as the public default-branch source available during this assessment. No separate local product checkout was supplied.

**The implementation details that drive the assessment**

1. **The current Spec Kit is a substantial workflow platform.** It would be inaccurate to assess it as only Markdown templates. Its engine persists run state, supports resume, and writes state atomically. Its gate step pauses without a TTY, handles rejection, and can accept a configured verdict input. Its command step actually dispatches to an integration CLI and fails when dispatch is unavailable. Shell steps capture exit codes and output. These are executable controls, although a successful agent process does not establish that its implementation satisfies the specification. Sources: [state persistence and engine](https://github.com/github/spec-kit/blob/fd490fac952cc6baeb421905b28031b4c5fe8a99/src/specify_cli/workflows/engine.py#L594), [gate implementation](https://github.com/github/spec-kit/blob/fd490fac952cc6baeb421905b28031b4c5fe8a99/src/specify_cli/workflows/steps/gate/__init__.py), [command execution](https://github.com/github/spec-kit/blob/fd490fac952cc6baeb421905b28031b4c5fe8a99/src/specify_cli/workflows/steps/command/__init__.py#L145), [shell execution](https://github.com/github/spec-kit/blob/fd490fac952cc6baeb421905b28031b4c5fe8a99/src/specify_cli/workflows/steps/shell/__init__.py).

2. **Spec Kit’s default quality path still has important gaps.** Its task-generation instructions only generate test tasks when the specification requests tests or the user requests TDD. Its bundled SDD workflow reviews the specification and plan, then runs tasks and implementation; it does not invoke analyze or converge. Converge does exist, but is an agent-mediated assessment that appends remediation tasks, not a deterministic proof of conformance. The converge instructions also explicitly tolerate an unfilled constitution. Some command templates instruct the agent to disclose malformed extension-hook YAML and continue, even though mandatory hooks may be unreadable. That is a material limitation for anyone treating these prompts as mandatory governance. It does not imply every executable hook path fails open. Sources: [optional test task rule](https://github.com/github/spec-kit/blob/fd490fac952cc6baeb421905b28031b4c5fe8a99/templates/commands/tasks.md#L147), [bundled workflow](https://github.com/github/spec-kit/blob/fd490fac952cc6baeb421905b28031b4c5fe8a99/workflows/speckit/workflow.yml), [converge rules](https://github.com/github/spec-kit/blob/fd490fac952cc6baeb421905b28031b4c5fe8a99/templates/commands/converge.md#L63), [hook parse-error behavior](https://github.com/github/spec-kit/blob/fd490fac952cc6baeb421905b28031b4c5fe8a99/templates/commands/tasks.md#L31).

3. **se_harness has a real structural model and revision-evidence system.** The artifact layout defines 14 types. The validator checks identifiers, relationships, lifecycle metadata, requirements coverage, and record consistency. Capture-verification requires appropriate work and verification states, exact agreement with declared verification contracts, a clean worktree, and candidate identity. Release validation checks candidate-commit agreement with verification records. The current repository contains 1,603 parsed formal artifacts and passed candidate-source validation with zero errors; its 46 warnings were all W013 maintenance warnings for valid records outside canonical locations. That shows substantial use of the model on its own repository, while leaving behavioral conformance to tests and review. Sources: [artifact layout](https://github.com/mmzen/se_harness/blob/e1eb96bf0909d9fdb62a177657af343dc24e9286/se_harness/artifact_layout.py#L17), [coverage validation](https://github.com/mmzen/se_harness/blob/e1eb96bf0909d9fdb62a177657af343dc24e9286/se_harness/engine/validation_architecture.py), [verification capture](https://github.com/mmzen/se_harness/blob/e1eb96bf0909d9fdb62a177657af343dc24e9286/se_harness/provenance.py#L436), [release consistency](https://github.com/mmzen/se_harness/blob/e1eb96bf0909d9fdb62a177657af343dc24e9286/se_harness/engine/validation_revision.py#L147).

4. **se_harness’s evaluator boundary is stronger than its human-identity boundary.** The mutation guard checks the configured evaluator version, lock, runtime origin, and evaluator evidence. This addresses the important problem of candidate code judging itself. However, the CLI describes its transition decision input as an ID=ACTOR assertion. Ordinary transition validation checks actor text; selected decision/release paths add role or owner checks, but these are still checks against repository declarations. I found no authenticated human-approval service in these paths. The policy makes role separation conditional on repository policy. Its native plugin explicitly has no automatic session or before-tool hooks, and ordinary edits use host permissions. Therefore, this is strong checking at explicit governance boundaries; it is not comprehensive prevention of every out-of-scope file edit. Sources: [mutation guard](https://github.com/mmzen/se_harness/blob/e1eb96bf0909d9fdb62a177657af343dc24e9286/se_harness/mutation_guard.py#L137), [transition CLI](https://github.com/mmzen/se_harness/blob/e1eb96bf0909d9fdb62a177657af343dc24e9286/se_harness/cli.py#L1022), [actor validation](https://github.com/mmzen/se_harness/blob/e1eb96bf0909d9fdb62a177657af343dc24e9286/se_harness/workflow_edges.py#L83), [decision-rights policy](https://github.com/mmzen/se_harness/blob/e1eb96bf0909d9fdb62a177657af343dc24e9286/templates/repository/standard/docs/engineering/DECISION_RIGHTS.md#L57), [native plugin boundaries](https://github.com/mmzen/se_harness/blob/e1eb96bf0909d9fdb62a177657af343dc24e9286/plugins/verity-plane/codex/README.md).

5. **Neither system proves that natural-language intent and code are equivalent.** Spec Kit delegates much of that judgment to the coding/review agent. Harness can require and bind evidence, but a structurally valid graph or record does not establish that a test adequately checks the requirement, that a reviewer was independent, or that the product works. Harness’s own operator guidance assigns semantic review and GitHub protections to humans or repository owners. The README describes the fully authoritative, continuously synchronized Virtual Twin as a vision. I credited its existing graph, validation, and evidence mechanisms, not that full future promise. Sources: [Harness scope and retained human responsibilities](https://github.com/mmzen/se_harness/blob/e1eb96bf0909d9fdb62a177657af343dc24e9286/docs/notes/harness-overview.md#L59), [Virtual Twin description](https://github.com/mmzen/se_harness/blob/e1eb96bf0909d9fdb62a177657af343dc24e9286/README.md), [Spec Kit convergence procedure](https://github.com/github/spec-kit/blob/fd490fac952cc6baeb421905b28031b4c5fe8a99/templates/commands/converge.md).

6. **The strongest practical tradeoff is process cost versus persistent control.** Spec Kit concentrates on producing and implementing a feature package. Harness carries authority and evidence through an ongoing product lifecycle, which is useful for changes in established repositories but imposes more state and authoring obligations. The native change skill already supports package drafting, continued authorized work, and explicit checkpoints; it deserves credit for reducing friction. There is still room for a much simpler first useful workflow without weakening the underlying contract. Sources: [Spec Kit lean preset](https://github.com/github/spec-kit/blob/fd490fac952cc6baeb421905b28031b4c5fe8a99/presets/lean/README.md), [Harness onboarding](https://github.com/mmzen/se_harness/blob/e1eb96bf0909d9fdb62a177657af343dc24e9286/docs/notes/getting-started.md), [Harness change skill](https://github.com/mmzen/se_harness/blob/e1eb96bf0909d9fdb62a177657af343dc24e9286/plugins/verity-plane/common/skills/change/SKILL.md).

- **Spec Kit broad selection:** tests/test_workflows.py, tests/workflows/, tests/integrations/test_manifest.py, and tests/integrations/test_integration_codex.py produced 1,246 passed, 7 skipped, and 36 failures. Inspection showed that all 36 failures were inability to create test symlinks under this Windows account (WinError 1314), before the behavior under test. They remain unverified locally; they are not evidence of 36 product defects.
- **Spec Kit focused mechanism selection:** the gate, shell, run-state, and workflow-engine selection produced 148 passed, 836 deselected. This overlaps the broad selection and must not be added to it.
- **Harness selection:** six modules covered work-order assurance, hash-bound integrity, workflow execution, revision provenance, mutation guards, and interpreter safety. A Git ownership mismatch and the incomplete index left by the initial Windows long-path checkout caused environment failures. After correcting ownership configuration, the six-module run had 191 tests with 6 skips and four failing subtests, all caused by the incomplete index. Repairing that index and rerunning the affected hash-integrity module yielded 56 tests, 3 skipped, no failures. The combined final result for the selected tests is 185 passed and 6 skipped, established through the selection plus the affected-module rerun.
- **Harness real corpus:** candidate-source validate returned valid=true, 1,603 artifacts, 0 errors, 46 W013 warnings, 0 advisories. This was a structural inspection, not a released-evaluator qualification or verification/release decision.

I did not run either complete suite, execute paid coding-agent sessions, compare the same implemented feature, authenticate owner decisions, or inspect live branch-protection settings. The comparison credits capabilities in the distributable harness separately from repository-specific release machinery. In particular, the full se_harness project’s publication/replay process is not automatically installed as every downstream project’s release pipeline. Its standard managed workflow does install an isolated evaluator and check declared PR work and scope. Source: [distributed workflow template](https://github.com/mmzen/se_harness/blob/e1eb96bf0909d9fdb62a177657af343dc24e9286/templates/repository/standard/.github/workflows/engineering-harness.yml).

**What I would prioritize for se_harness**

1. **Make authority provenance explicit.** Document actor strings as assertions at every relevant interface. For teams requiring stronger controls, provide an adapter that binds a decision to a host-authenticated review or approval, the candidate commit, artifact versions, and evidence digest. Keep those checks distinct from evaluator identity.
2. **Reduce the first-change workflow.** Build on the existing setup/change/evidence skills to draft one coherent package, show what is incomplete, and request the exact decision only once its inputs are reviewable. Use progressive disclosure so users do not need to learn the whole artifact taxonomy before their first change.
3. **Integrate with specification tools through one authoritative model.** A proposed Spec Kit adapter could turn spec/plan/tasks into draft Harness artifacts and map user stories, requirements, tasks, and verification obligations. It would need explicit handling of amendments and stable identifiers. Harness should remain responsible for legal transitions and assurance; generated documents should not independently authorize work.
4. **Add comparative end-to-end evidence.** Run the same new feature, brownfield change, and bug fix through both systems. Measure setup effort, authoring/edit burden, blocked invalid changes, stale-evidence detection, escaped defects, and total model/tool cost. The present source review cannot establish those outcome differences.

For Spec Kit, the highest-value governance improvements would be a bundled mandatory-quality profile: explicit tests and executable checks, fail-closed handling of unreadable mandatory hooks, a convergence step in the automated default cycle, retained command evidence, and commit-bound approval/verification records. The default streaming integration path currently returns empty stdout/stderr and applies no timeout while streaming, which limits unattended-run evidence and bounded execution. Source: [integration dispatch implementation](https://github.com/github/spec-kit/blob/fd490fac952cc6baeb421905b28031b4c5fe8a99/src/specify_cli/integrations/base.py#L393).

The repositories also make different licensing choices: Spec Kit carries the [MIT license](https://github.com/github/spec-kit/blob/fd490fac952cc6baeb421905b28031b4c5fe8a99/LICENSE); se_harness carries [GPLv3](https://github.com/mmzen/se_harness/blob/e1eb96bf0909d9fdb62a177657af343dc24e9286/LICENSE). I have not scored legal suitability or inferred the obligations of any particular downstream integration.

**Recommendation:** use Spec Kit when the primary objective is accessible, extensible agent-assisted feature delivery. Use se_harness when traceability, bounded work, evidence freshness, and accountable verification/release are central requirements. For the development of se_harness itself, preserve the governance/evidence core and borrow Spec Kit’s stronger authoring and integration experience.
