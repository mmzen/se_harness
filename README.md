# SE Harness

**SE Harness is an agentic software engineering harness that turns a coding agent into a governed execution system, driving work from requirement to validated change with built-in context, constraints, verification, traceability, and evidence.**

It makes a repository-native, specification-driven engineering workflow repeatable across new and existing repositories. Each installation provides the same complete harness: engineering artifact templates, validation, the Harness Explorer dashboard, agent instructions, evidence structures, and CI integration.

The goal is not simply to generate code faster. SE Harness helps ensure that a software change can be traced back to its intent and requirements, verified against its specifications and engineering constraints, and supported by objective evidence for quality, release, and compliance assessment.

## Quick start

Use Python 3.11 or later from this cloned repository:

```powershell
python -m se_harness init C:\path\to\new-repository --project-name my-project
python -m se_harness adopt C:\path\to\existing-repository --project-name my-project
```

- `init` bootstraps an empty or absent target repository.
- `adopt` scans an existing repository, preserves existing files, and creates an adoption report.
- Adoption never invents product intent: humans must explicitly define and approve intent before the agent can treat it as authoritative.

Operate an installed harness with:

```powershell
python -m se_harness doctor C:\path\to\repository
python -m se_harness validate C:\path\to\repository
python -m se_harness dashboard C:\path\to\repository
python -m se_harness capture-verification C:\path\to\repository --id VREC-001 --work-order WO-001 --verification VER-001 --evidence docs/engineering/DOMAIN/evidence/WO-001-verification.md
python -m se_harness prepare-release C:\path\to\repository --id RLS-001 --release-contract REL-001 --verification-record VREC-001 --work-order WO-001 --version 1.0.0 --authorized-by release-owner
python -m se_harness upgrade C:\path\to\repository
python -m se_harness upgrade C:\path\to\repository --apply
```

The dashboard is generated by default at:

```text
target/harness-dashboard/index.html
```

## What the harness provides

The harness gives a coding agent the engineering context and control structure required to execute work consistently:

- structured intent, requirements, specifications, architecture, and engineering decisions;
- repository-local instructions and execution rules for the agent;
- explicit quality, security, architecture, and engineering constraints;
- artifact and repository validation;
- verification workflows tied to acceptance criteria and expected behavior;
- traceability from intent and requirements to specifications, implementation, tests, and delivery;
- an evidence chain supporting why a delivered change is considered valid;
- CI integration so harness rules and checks are continuously enforced;
- a Harness Explorer dashboard to inspect engineering artifacts, traceability, validation state, and evidence.

The objective is to make **requirement-to-change execution repeatable, inspectable, governed, and evidence-backed**.

## Engineering model

SE Harness structures software engineering around an explicit chain from intent to delivered behavior:

```text
Intent
  ↓
Requirements
  ↓
Specifications / Architecture
  ↓
Implementation
  ↓
Verification
  ↓
Evidence
  ↓
Release / Deployment
```

The coding agent operates within this structure rather than treating the repository as an unconstrained code-generation environment.

Human-defined intent, requirements, architecture, policies, and release authority remain explicit inputs to the process.

## Evidence and assurance

SE Harness treats **evidence as a first-class engineering artifact**.

The objective is not only to produce a software change, but to retain objective, inspectable evidence that the implementation satisfies its intended requirements, specifications, and engineering constraints.

Evidence can include:

- traceability from intent and requirements to specifications and implementation;
- identification of the code changes implementing a requirement or specification;
- acceptance criteria and their verification results;
- unit, integration, system, regression, and performance test results;
- code coverage and quality metrics;
- static analysis and linting results;
- security scans and dependency analysis;
- architecture and policy conformance checks;
- review and approval records;
- build and CI/CD results;
- release and deployment evidence;
- runtime and observability evidence where production behavior is part of the requirement.

The resulting evidence chain answers four fundamental questions:

```text
What was required?
        ↓
What was implemented?
        ↓
How was it verified?
        ↓
What evidence supports the conclusion?
```

This evidence can support:

- engineering quality assessment;
- change and release decisions;
- internal control reviews;
- security assessment;
- architecture governance;
- audit preparation;
- compliance evidence collection.

SE Harness does not itself declare regulatory compliance. It provides structured and reproducible engineering evidence that can be mapped to applicable quality, security, and compliance requirements.

This makes the harness suitable as a foundation for higher-level assurance workflows such as ISO 27001, SOC 2, NIST, FedRAMP, DORA, or organization-specific engineering controls.

## Traceability

Traceability connects engineering artifacts across the lifecycle so that a change can be understood in context.

A requirement should be traceable to the specifications and architecture that constrain it, the implementation that realizes it, and the verification evidence demonstrating expected behavior.

Conceptually:

```text
Intent
  └── Requirement
        ├── Specification
        ├── Architecture decision
        ├── Implementation
        ├── Acceptance criteria
        ├── Tests
        └── Evidence
```

Traceability provides the structure.

Evidence provides the basis for confidence.

Together they allow a reviewer, agent, quality engineer, release authority, or auditor to determine not only **what changed**, but **why the change should be trusted**.

## Safety model

- Installation is planned completely before any file is written.
- Ordinary file conflicts stop initialization or adoption without partial writes.
- Existing `AGENTS.md` and `.gitignore` files receive bounded managed blocks rather than being replaced.
- A lock file records hashes of tool-owned content.
- Upgrades change only unmodified managed content; customized files are preserved for manual review.
- Adoption inventories repository signals but never infers approved product intent, requirements, architecture, or release authority.
- Verification and release preparation records a full clean candidate commit but creates only `ready` artifacts; it never commits, tags, approves, releases, or publishes.

## Commit-bound lineage

The authoritative path is:

```text
Intent -> Capability -> Requirement -> Work order
       -> Verification record at candidate commit C
       -> Release record for the same commit C
       -> Operating assurance
```

Commit the candidate source and retained evidence first. `capture-verification` then creates a ready `VREC-*` naming that earlier candidate. Commit this record in a later governance commit, obtain assurance review, and use `prepare-release` to create a ready `RLS-*`. This ordering avoids an impossible file that attempts to contain the hash of its own commit.

The dashboard distinguishes declared candidate commits from the currently observed checkout and reports `exact`, `different`, or `not assessable` comparison state.
- Human-defined intent and authority remain explicit inputs to the engineering process.
- Generated implementation is not considered valid solely because an agent produced it; verification and evidence remain separate concerns.
- Missing evidence must remain visible rather than being silently interpreted as successful verification.
